GraphRAG & Self-Corrective Hybrid Retrieval Engine — Complete Project Guide

The single document that explains everything: what this project is, why every technology was chosen, how data flows through the system, what every file does, how to run and operate it, measured performance, real use cases, honest limitations, and the roadmap ahead.

1. WHAT — the one-paragraph summary

A production-style Graph-Enhanced Hybrid RAG platform that answers questions over a document collection by combining four retrieval signals — dense vector search, sparse lexical search, knowledge-graph traversal, and cross-encoder reranking — fused with Reciprocal Rank Fusion, and wrapped in a self-corrective CRAG loop (grade → rewrite → web fallback) orchestrated by a LangGraph state machine. It ships with an automated Ragas/DeepEval evaluation harness, a FastAPI service, a Streamlit console, Celery-based async ingestion, and a curated multi-hop benchmark dataset. Everything runs on free, self-hostable resources.

2. WHY — the problem it solves

Standard vector-only RAG fails on enterprise knowledge bases in three ways:

Failure mode Example How this project fixes it
No global entity awareness “Which supplier’s part caused incident X?” — the answer spans 3 documents Neo4j graph connects Product → Component → Supplier → Incident via extracted relations
Keyword-blind semantic search SKU / incident-ID / policy-code lookups (“INC-1042”, “SEC-14”) Sparse lexical vectors (BGE-M3) match exact identifiers dense models miss
Blind faith in retrieval Irrelevant chunks silently poison the answer CRAG loop grades every retrieval; weak evidence triggers query rewriting or a web fallback
No quality measurement “Is my RAG good?” answered by vibes Ragas + DeepEval harness over a golden multi-hop dataset, runnable in CI

6. WORKFLOW — what happens on every question, millisecond by millisecond

Measured warm trace (Groq + CPU reranker, sample corpus):

# Stage Typical ms What actually runs
1 vector_search 100–500 BGE-M3 encodes the question once → two Qdrant queries (dense ANN top-10, sparse top-10). Runs in a parallel thread with stage 2
2 graph_search 26–190 Regex keywords → Entity CONTAINS match → 2-hop RELATED expansion → chunks via MENTIONS (direct-entity chunks ranked first = hop decay). If zero entities matched, one guarded text2Cypher LLM call attempts a traversal (adds ~1.5 s — this is why it is skipped whenever keyword matching succeeds)
3 rrf_fusion ~0 Reciprocal Rank Fusion (k=40) over the 3 rankings; dedupe by chunk id
4 rerank ~1500 Top 16 fused candidates scored by the cross-encoder (600-char pairs, max_length 512) → sorted, floor-pruned, top 6 kept
5a grade_documents 0 or ~1100 Fastpath: if the best rerank score ≥ 0.78, grading is skipped entirely. Otherwise one batched LLM call grades all 6 docs (relevant/irrelevant + reason)
5b rewrite_query 0 or ~1000 Only when grading finds nothing relevant: LLM rewrites the query using grader feedback; loop retrieves once more (hard cap 1 iteration)
5c web_fallback ~1–2 s Only when rewriting still fails: DuckDuckGo top-3 snippets enter the context, clearly labeled
6 generate 500–800 Numbered context blocks + question → Groq (reasoning_effort=low) → concise cited answer
— end-to-end 2100–2500 stop_reason tells you which path ran: generated_fastpath / generated / generated_with_web

7. INGESTION WORKFLOW — how documents become a knowledge graph

  1. Load (loaders.py): PDF via pypdf, md/txt direct. Title = first markdown heading, else filename. doc_id = slug(filename) + sha1(absolute_path)[:8] → re-uploading the same file updates it (MERGE semantics), never duplicates.
  2. Chunk (chunking.py): paragraphs merged greedily to ~800 chars; oversized paragraphs are hard-sliced with overlap; noise (<60 chars) dropped. Adjacent chunks linked [:NEXT] to preserve reading order.
  3. Extract (extractor.py → schema.py): one Instructor JSON-mode call per chunk returns ChunkExtraction: up to 12 entities (name, type from a fixed allow-list, description) and 8 relations (source, target, UPPER_SNAKE relation_type, evidence). Failed chunks are skipped gracefully — indexing never aborts.
  4. Summarize: one call per document → stored on the :Document node and embedded as a kind="summary" vector, so document-level questions retrieve the summary itself.
  5. Graph write (neo4j_store.py): single write transaction per document — MERGE document, chunks, NEXT chain, entities (keyed by slugified name → cross-document dedup), MENTIONS, RELATED {type, evidence} edges.
  6. Vector write (qdrant_store.py): chunk texts + the summary embedded with BGE-M3 → upserted with payload {key, doc_id, title, kind}. Point IDs are uuid5 of the chunk key → idempotent re-ingest.

With Groq: ~1–3 s per chunk; the 16-doc corpus indexes in ~7 minutes; a 20-page PDF ≈ 1–2 min.

12. DESIGN DECISIONS & RATIONALE (the “why” behind the “what”)

  1. RRF over weighted fusion — rank-based, parameter-light, robust to unnormalized scores from three heterogeneous systems (cosine, lexical, graph hops). An alpha knob would add tuning burden with no measurable gain at this scale.
  2. One embedder for dense + sparse (BGE-M3) — a single model produces both signal types, so hybrid search costs one encoding pass and the index stays consistent.
  3. MERGE-based idempotent ingestion — doc_id is content-addressed from the file path; re-uploading updates in place. Safe retries, no duplicate corpora.
  4. Regex Cypher guard instead of an LLM safety prompt — deterministic, zero-latency, blocks any write/procedure/multi-statement; the LLM only ever sees read-only execution.
  5. Batch grading — one LLM call grades all 6 contexts (numbered excerpts → structured list), ~6x cheaper than per-doc calls.
  6. Reranker confidence as a grading bypass — the cross-encoder already “graded” every candidate; when its top score is high, a second LLM opinion is pure latency. Threshold 0.78 was chosen from observed score distributions (clear wins score 0.9+; ambiguous 0.5–0.75).
  7. Hop decay by ordering, not scoring — RRF consumes rank order, so placing direct-entity chunks ahead of 2-hop chunks implements γ-decay for free.
  8. Parallel stage threads — vector and graph retrieval are independent given the question; running them concurrently hides the smaller cost entirely.
  9. Fastpath + single rewrite iteration — live inference favors answering over perfection; the web fallback catches the residue. Deep correction is for offline pipelines, not chat.
  10. Reasoning-effort=low + prompt-level conciseness — gpt-oss spends tokens “thinking”; capping effort and asking for 2–5 sentences cut generation time ~40% without hurting groundedness (hard token caps were rejected — they truncate reasoning and yield empty JSON).
  11. Injectable CRAG components — the LangGraph wiring takes callables, so the whole loop is unit-tested with fakes, no LLM or stores required (see tests/test_crag_flow.py).

14. HONEST LIMITATIONS

  • Reranker on CPU (~1.5 s) is the floor of warm latency; MPS/GPU would take it to ~150 ms.
  • gpt-oss reasoning tokens add ~0.5 s even at low effort; a non-reasoning model is faster.
  • Extraction quality tracks the LLM: small local models miss relations; gpt-oss extracts richer graphs. Re-ingest after switching providers for best graphs.
  • text2Cypher is best-effort — guarded and optional; complex aggregations may return empty and the pipeline falls back gracefully.
  • Single-tenant, no auth — demo-grade; do not expose port 8000 publicly as-is.
  • Formats: pdf/md/txt only (no docx/html/OCR yet). Scanned PDFs without a text layer yield nothing.
  • Ragas with a local judge LLM is slow (~3 min for 2 cases); use Groq for the judge.
  • Chunk-level graph links mean very small documents produce one chunk and fewer relations.

15. FUTURE IMPROVEMENTS (prioritized roadmap)

  1. GPU/MPS reranking — auto-device detection; ~10x on the last big latency item.
  2. Graph communities — Leiden clustering + community summaries (Microsoft GraphRAG style) for “global” thematic questions (“what are the main quality themes across all suppliers?”).
  3. Query decomposition — split compound questions into sub-queries, retrieve per sub-query, merge — improves multi-hop precision further.
  4. Streaming responses — SSE token streaming into the UI for perceived latency <1 s.
  5. Conversation memory — multi-turn sessions with entity tracking and follow-up rewriting.
  6. Feedback loop — 👍/👎 in the UI appends to the eval dataset; nightly Ragas regression gate in CI (fail the build if faithfulness drops >0.05).
  7. Docx/HTML ingestion + OCR fallback for scanned PDFs.
  8. Incremental folder watch — auto-ingest on file change (watchdog).
  9. Auth + multi-tenancy — API keys, per-tenant collections/graph labels.
  10. ColBERT late-interaction as an optional third retrieval signal.
  11. Kubernetes/Helm packaging + Prometheus metrics on stage latencies.
  12. Embedding versioning — model fingerprint per point; automatic re-embed on model change.

17. GLOSSARY

CRAG — Corrective RAG: grade retrievals, rewrite the query or fall back to the web when evidence is insufficient. RRF — Reciprocal Rank Fusion: score = Σ 1/(k + rank) across rankings. Dense/sparse vectors — semantic embeddings vs learned lexical weights (ID/SKU matching). Cross-encoder rerank — scoring query+document jointly for precision. Fastpath — skipping the LLM grader when reranker confidence is high. Hops — graph relationship traversals from a matched entity.
